Kubernetes Workshop: Deploy a Full-Stack App on K3s

Workshop Goals

In this workshop you will write Kubernetes manifests from scratch to deploy a full-stack CRUD application (Node.js backend, Nginx frontend, PostgreSQL database) on a K3s cluster. By the end you will understand:

  • How to build and import container images into K3s
  • How to create Deployments to run containerized workloads
  • How to expose applications with Services (ClusterIP and NodePort)
  • How to configure Horizontal Pod Autoscalers for automatic scaling
  • How to provision persistent storage with PersistentVolumes and PersistentVolumeClaims
  • How Kubernetes resources depend on each other and how DNS-based service discovery works

Prerequisites

  • A running K3s cluster (single-node is fine)
  • kubectl installed and configured to connect to your cluster (use sudo kubectl if permissions require it)
  • Container images built and imported into K3s:
    • sudo docker build -t workshop-backend:latest ./backend
    • sudo docker build -t workshop-frontend:latest ./frontend
    • sudo docker save workshop-backend:latest | sudo k3s ctr images import -
    • sudo docker save workshop-frontend:latest | sudo k3s ctr images import -
  • Basic familiarity with YAML syntax
Important: K3s uses containerd, not Docker. Images built with docker build must be imported into K3s with docker save | k3s ctr images import. All Deployments use imagePullPolicy: Never to prevent K3s from trying to pull from a remote registry.
Task 1

Backend Deployment

Create a Kubernetes Deployment resource for the backend (Node.js Express API) component. The Deployment ensures your backend container runs with the correct environment variables for database connectivity.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  labels:
    app: workshop
    component: <COMPONENT_NAME>
spec:
  replicas: <REPLICA_COUNT>
  selector:
    matchLabels:
      app: workshop
      component: <COMPONENT_NAME>
  template:
    metadata:
      labels:
        app: workshop
        component: <COMPONENT_NAME>
    spec:
      containers:
        - name: backend
          image: <IMAGE_NAME>
          imagePullPolicy: Never
          ports:
            - containerPort: <PORT>
              name: http
          env:
            - name: DB_HOST
              value: <DATABASE_SERVICE_NAME>
            - name: DB_PORT
              value: "<DB_PORT>"
            # Add remaining env vars: DB_NAME, DB_USER, DB_PASSWORD, PORT
          resources:
            requests:
              cpu: <CPU_REQUEST>
              memory: <MEM_REQUEST>
            limits:
              cpu: <CPU_LIMIT>
              memory: <MEM_LIMIT>
The component label should be backend — this label is used to tie the Deployment, Service, and HPA together.
Use workshop-backend:latest as the image. The Express server listens on port 3000 by default.
Set DB_HOST to the name of the PostgreSQL Service you will create later (e.g. postgres-service). Set DB_PORT to 5432.
imagePullPolicy: Never tells K3s to use locally imported images instead of trying to pull from a remote registry. Always set this for images built and imported locally.
Task 2

Backend Service (ClusterIP)

Create a Service resource of type ClusterIP for the backend component. This Service gives the backend a stable internal DNS name so the frontend can reach it within the cluster.

apiVersion: v1
kind: Service
metadata:
  name: <SERVICE_NAME>
  labels:
    app: workshop
    component: backend
spec:
  type: <SERVICE_TYPE>
  selector:
    app: <???>
    component: <???>
  ports:
    - name: http
      port: <SERVICE_PORT>
      targetPort: <TARGET_PORT_NAME>
      protocol: TCP
Use ClusterIP — this makes the service accessible only within the cluster. The frontend will proxy requests to it.
The selector must exactly match the pod template labels from your backend Deployment: app: workshop and component: backend.
Set port: 3000 (the port the Service listens on) and targetPort: http (referencing the named port on the container).
Task 3

Frontend Deployment

Create a Kubernetes Deployment for the frontend component (Nginx serving static files). The frontend container needs an environment variable pointing to the backend service for API proxying.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  labels:
    app: workshop
    component: <COMPONENT_NAME>
spec:
  replicas: <REPLICA_COUNT>
  selector:
    matchLabels:
      app: workshop
      component: <COMPONENT_NAME>
  template:
    metadata:
      labels:
        app: workshop
        component: <COMPONENT_NAME>
    spec:
      containers:
        - name: frontend
          image: <IMAGE_NAME>
          imagePullPolicy: Never
          ports:
            - containerPort: <PORT>
              name: http
          env:
            - name: BACKEND_URL
              value: <BACKEND_SERVICE_URL>
          resources:
            requests:
              cpu: <CPU_REQUEST>
              memory: <MEM_REQUEST>
            limits:
              cpu: <CPU_LIMIT>
              memory: <MEM_LIMIT>
Use workshop-frontend:latest as the image. Nginx listens on port 80.
Set BACKEND_URL to the backend Service's full cluster DNS name: http://backend-service.default.svc.cluster.local:3000. The FQDN is required because the Nginx resolver doesn't use Kubernetes search domains.
Task 4

Frontend Service (NodePort)

Create a Service of type NodePort for the frontend component. This exposes the frontend on a fixed port on every cluster node so you can access it from your browser.

apiVersion: v1
kind: Service
metadata:
  name: <SERVICE_NAME>
  labels:
    app: workshop
    component: frontend
spec:
  type: <SERVICE_TYPE>
  selector:
    app: <???>
    component: <???>
  ports:
    - name: http
      port: <SERVICE_PORT>
      targetPort: <TARGET_PORT_NAME>
      nodePort: <NODE_PORT>
      protocol: TCP
Use type NodePort. Choose a port in the range 30000-32767. A good default is 30080.
Set port: 80 for the service port and targetPort: http to match the named port on the frontend container.
Task 5

Database Deployment

Create a Deployment for the PostgreSQL database component. This requires environment variables for initial database configuration, a volume mount for data persistence, and optionally an init script via ConfigMap.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  labels:
    app: workshop
    component: <COMPONENT_NAME>
spec:
  replicas: 1
  selector:
    matchLabels:
      app: workshop
      component: <COMPONENT_NAME>
  template:
    metadata:
      labels:
        app: workshop
        component: <COMPONENT_NAME>
    spec:
      containers:
        - name: postgres
          image: <POSTGRES_IMAGE>
          ports:
            - containerPort: <PORT>
              name: postgres
          env:
            - name: POSTGRES_DB
              value: <DB_NAME>
            - name: POSTGRES_USER
              value: <DB_USER>
            - name: POSTGRES_PASSWORD
              value: <DB_PASSWORD>
          resources:
            requests:
              cpu: <CPU_REQUEST>
              memory: <MEM_REQUEST>
            limits:
              cpu: <CPU_LIMIT>
              memory: <MEM_LIMIT>
          volumeMounts:
            - name: postgres-data
              mountPath: <DATA_DIR>
      volumes:
        - name: postgres-data
          persistentVolumeClaim:
            claimName: <PVC_NAME>
Use postgres:15-alpine for a lightweight PostgreSQL 15 image.
PostgreSQL stores data at /var/lib/postgresql/data. Mount your PVC there.
The env values must match what the backend expects: POSTGRES_DB: workshop, POSTGRES_USER: workshop, POSTGRES_PASSWORD: workshop123.
Task 6

Database Service (ClusterIP)

Create a Service of type ClusterIP for the PostgreSQL database. The backend Deployment references this service by name as its DB_HOST, so the name must match exactly.

apiVersion: v1
kind: Service
metadata:
  name: <SERVICE_NAME>
  labels:
    app: workshop
    component: postgres
spec:
  type: <SERVICE_TYPE>
  selector:
    app: <???>
    component: <???>
  ports:
    - name: postgres
      port: <SERVICE_PORT>
      targetPort: <TARGET_PORT>
      protocol: TCP
Name it postgres-service — this must match the DB_HOST environment variable in the backend Deployment.
PostgreSQL uses port 5432. Set both port and targetPort to 5432.
Task 7

Horizontal Pod Autoscaler for Backend

Create a HorizontalPodAutoscaler (HPA) resource that automatically scales the backend Deployment based on CPU utilization. This ensures the backend can handle traffic spikes.

apiVersion: <API_VERSION>
kind: HorizontalPodAutoscaler
metadata:
  name: backend-hpa
  labels:
    app: workshop
    component: backend
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: <TARGET_KIND>
    name: <TARGET_NAME>
  minReplicas: <MIN>
  maxReplicas: <MAX>
  metrics:
    - type: <METRIC_TYPE>
      resource:
        name: <RESOURCE_NAME>
        target:
          type: <TARGET_TYPE>
          averageUtilization: <THRESHOLD>
Use autoscaling/v2 for K3s compatibility. This version supports the metrics array syntax.
Set kind: Deployment and name: backend to reference your backend Deployment.
Use type Resource, resource name cpu, target type Utilization, and set averageUtilization: 70. Scale between 1 and 5 replicas.
Task 8

PersistentVolume and PersistentVolumeClaim

OPTIONAL

Create a PersistentVolume (PV) using a local hostPath and a matching PersistentVolumeClaim (PVC) for the PostgreSQL database. This gives the database durable storage that survives pod restarts.

These resources are optional. Without them, database data is lost if the pod restarts. The PVC name here must match the claimName you used in Task 5.

PersistentVolume

apiVersion: v1
kind: PersistentVolume
metadata:
  name: <PV_NAME>
  labels:
    app: workshop
    component: postgres
spec:
  storageClassName: <STORAGE_CLASS>
  capacity:
    storage: <CAPACITY>
  accessModes:
    - <ACCESS_MODE>
  hostPath:
    path: <HOST_DIRECTORY>

PersistentVolumeClaim

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: <PVC_NAME>
  labels:
    app: workshop
    component: postgres
spec:
  storageClassName: <STORAGE_CLASS>
  accessModes:
    - <ACCESS_MODE>
  resources:
    requests:
      storage: <REQUESTED_STORAGE>
Use storageClassName: manual on both the PV and PVC so they bind to each other.
Set capacity to 1Gi and access mode to ReadWriteOnce. The PVC request should not exceed the PV capacity.
Use a path like /data/workshop-postgres for the hostPath. Name the PVC postgres-pvc to match the Deployment volume reference.
